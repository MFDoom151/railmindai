# Архитектура «Цифровой станции»

![архитектура](architecture.svg)

## 1. Принципы

* **Состояние строится только из событий.** Симулятор — один из источников; любой внешний датчик может слать те же события по WebSocket/HTTP.
* **Модульный монолит.** Каждый блок — отдельный модуль со строгим интерфейсом (`backend/digital/*`). Шина событий, нормализатор и планировщик
  можно вынести в отдельные процессы/контейнеры (Kafka/RabbitMQ вместо in-process pub/sub) без изменения доменной логики.
* **Быстрый ответ + точный ответ.** На любое изменение обстановки сначала публикуется мгновенный план (эвристика, единицы мс), затем — оптимальные
  варианты CP-SAT (≈1–2 с). UI показывает оба и время расчёта.
* **Конфигурация без перекомпиляции** (YAML + API), **секреты только из окружения**.

## 2. Модули (`backend/digital/`)

| Модуль | Ответственность |
|---|---|
| `config.py` | YAML + override, валидация (pydantic), горячая перезагрузка, подписчики на изменения |
| `infra.py` | цифровая модель инфраструктуры: пути, парки (П/С/Пл), платформы, длины, горловины, окна ТО, локомотивы, бригады |
| `timetable.py` | детерминированный генератор расписания (грузовые с переработкой, пассажирские, транзит) по профилю станции |
| `simulator.py` | «поле»: исполняет план, физика занятости, нештатные ситуации, шум канала (дубли, потери, порядок, мусор) |
| `ingest.py` | валидация, дедупликация, буфер переупорядочивания, отбраковка устаревших, EMA-сглаживание, счётчики и задержки |
| `state.py` | наблюдаемое состояние станции + живые KPI для индекса |
| `planner.py` | CP-SAT и списочная эвристика, параллельные варианты |
| `conflicts.py` | детектор конфликтов (9 типов) и генерация вариантов разрешения |
| `efficiency.py`, `kpi.py` | индекс эффективности, KPI плана (прогноз индекса по варианту) |
| `service.py` | оркестратор станции (цикл ≥1 Гц), нештатные ситуации, альтернативы, рассылка, снимки |
| `store.py` | SQLite: снимки, события, планы; фоновая запись, срок хранения |
| `api.py` | REST, WebSocket, SSE, приём данных, отчёты |
| `auth.py`, `metrics.py`, `reports.py` | роли и токены, Prometheus-метрики и логи, PDF/CSV |

## 3. Протокол событий (вход)

```json
{"kind":"train_pos","entity":"Г-2041","seq":17,"ts":523.5,"p":{"phase":"on_track","track":3,"prog":1.0,"pos_m":212.0,"speed":0.0},"src":"sim","wt":1699999999.1}
```
Виды: `sim_clock`, `train_sched`, `train_eta`, `train_pos`, `train_op`, `resource` (локомотив/бригады), `track` (закрытие), `env` (питание ЭЦ).
`seq` монотонен по сущности (дедупликация), `ts` — модельное время (порядок), `wt` — wall-time создания (замер задержки).

## 4. Модель планирования (CP-SAT)

Для каждого поезда: путь `x[i,t]`, время начала приёма `arr_i`, время отправления `dep_i ≥ max(S_i, конец последней операции + готовность)`,
операции (осмотр, роспуск, подформирование) с назначением локомотива `y[o,k]`.

Жёсткие ограничения: отсутствие пересечений (NoOverlap) на **путях**, во **входной (L)** горловине (приёмы + манёвры) и **выходной (R)**,
у **локомотивов** и на **сортировочных путях**; кумулятивное ограничение по **бригадам**; окна ТО и закрытия путей; платформа — только пассажирским;
длина состава ≤ длины пути; недоступность локомотивов/бригад; транзит — фиксированные интервалы.
Цель: `Σ вес(приоритет)·(w_late·опоздание_отправления + w_wait·ожидание_приёма) + w_change·смены_пути` (устойчивость плана).
Подсказки (hints) от предыдущего плана ускоряют решение и сохраняют стабильность. Закрытие пути под стоящим составом вступает в силу после его отправления.

**Альтернативы при сбое:** «без вмешательства» (FIFO по прежним назначениям), быстрый, «минимум опозданий», «минимум изменений», «приоритетные первыми»,
«минимум очереди», «защита пассажирских», «с резервным ресурсом» — параллельно, ядра CPU делятся между вариантами. Для каждого: время расчёта,
Σ опозданий, число конфликтов, число смен пути, **прогноз индекса** и его Δ к «без вмешательства».

## 5. Индекс эффективности

`Индекс = 100 · Σ wₖ·fₖ / Σ wₖ`, где `fₖ ∈ [0,1]` — кусочно-линейная оценка фактора по порогам из конфигурации.
Факторы (веса по умолчанию): пропускная способность 0.18, среднее отклонение от графика 0.18, наибольшее отклонение 0.07, загрузка путей 0.12 (оптимум — рабочий диапазон),
конфликты 0.18, очередь на подходе 0.07, загрузка локомотивов 0.10, загрузка бригад 0.10. Категории: **Норма ≥ 75**, **Внимание 50–75**, **Критично < 50**; буквы A–E (90/80/65/50).
Вклад каждого фактора в потерю индекса: `100·wₖ·(1−fₖ)/Σw`; в интерфейсе — топ-5 с исходным значением и подсказкой, формула доступна по кнопке.

## 6. Данные и история

* Онлайн: кадры `state` (≥ 2 Гц), события `plan`, `conflicts`, `alternatives`, `alert`; новому подписчику — `hello` (инфраструктура, формула индекса),
  текущий план, конфликты, альтернативы, журнал и `backfill` последних кадров. Медленный клиент теряет старые кадры, но не тормозит цикл.
* Перемотка: клиент хранит последние 15 минут кадров (1800), сервер — столько же в памяти + `/replay`; долгая история — SQLite (`/history`, `/events`, `/plans`).
* SQLite: `snapshots` (раз в 5 с), `events` (сбои, конфликты, смена плана), `plans`; срок хранения 72 ч.

## 7. Безопасность

Роли: `viewer` (без входа: просмотр, отчёты), `dispatcher` (внесение ситуаций, применение планов, приём данных), `admin` (настройки индекса/ограничений/оптимизации).
Токены HMAC-SHA256 с TTL, ограничение попыток входа. Учётные данные и ключ — из `RAILTWIN_*` (см. `.env.example`); без них включается DEV-режим с демо-учётками и предупреждением в логе.
Данные синтетические; реальных коммерческих данных нет.

## 8. Наблюдаемость

`/health`, `/ready`, `/metrics` (Prometheus): тики и их длительность, `railtwin_replan_seconds{stage}`, события ingest (received/applied/invalid/duplicates/stale),
p95 задержки конвейера, лаг цикла событий, число WS-клиентов и сброшенных кадров, индекс и конфликты по станциям. Логи — JSON (`slow_tick`, `replan`).

## 9. Ограничения прототипа (честно)

* Данные и поведение станции синтетические; модель упрощена (маршруты — через две горловины, время в минутах).
* Шина событий — in-process; для горизонтального масштабирования заменить на брокер (интерфейсы `push`/`publish` уже изолированы).
* CP-SAT с лимитом времени возвращает лучшее найденное решение, не всегда доказанный оптимум (статус и bound возвращаются в `solver`).
* Мгновенность «быстрого» плана обеспечивает эвристика; качество ниже CP-SAT на сложных сбоях (это видно в таблице альтернатив).
